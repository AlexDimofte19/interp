11. Why the comp 0.6/0.8/1.0 cells were so slow
	Not grid size. Every per-step cost in the script scales with the LENGTH OF THE
	REASONING CHAIN, and the high-complexity trajectories reason far longer. Per
	step, with 700 analysis tokens and layers 7:23 (17 layers), that is ~11.9k CSV
	rows and ~11.9k .pt files. Measured shapes come from the one trajectory we have
	locally (size11 comp1.0 run 987: prefix 414, grid 297, suffix 3, 157 analysis
	tokens in its single step).
	The GPU was never the problem. Per step:
	    forward pass (~2.5k tokens, 3.6B active)     ~0.1-0.5 s
	    lens matmuls (17 x [700,2880]@[2880,201088])  ~0.15 s
	against filesystem + Python work one to two orders of magnitude larger. The
	four things actually eating the time:
	    a) one torch.save per (token, layer), fully serial
	    b) tok.decode([i]) x TOP_K per row - 238k Rust round-trips per step
	    c) 11.9k individual .cpu() copies in extract_activations_single_pass, then
	       a re-upload of the same values for the lens
	    d) lens["J"][layer].float().to(dev) inside the STEP loop - 566 MB of H2D
	       per step for matrices that never change
	Plus torch.cuda.empty_cache() every step (a sync, and it discards the caching
	allocator) and 11.9k separate writer.writerow calls.

12. What changed [DONE]
	All semantics-preserving. Same tree, same rows, every token kept - checked, not
	assumed (see 13).
	12.1 ActivationWriter (gather_activations_utils.py): thread pool over the same
	     mkdir + torch.save calls, so the .pt writes overlap the next forward pass.
	     --io-workers, default 16. Drained before the CSV is os.replace'd and worker
	     exceptions re-raised there, so a failed write cannot be skipped as done.
	     save_activations_to_files is now a wrapper around it (max_workers=0), so
	     gather_activations itself is unchanged.
	12.2 decode memo, J hoisted out of the loop and applied as one bmm
	     (apply_lens_transport), extract_activations_batched returning one stacked
	     (N,d) tensor per layer, writerows instead of writerow, empty_cache dropped,
	     --batch-size defaulting to 256 rather than "whole step".
	12.3 --forward-batch-size (default 4) / --forward-batch-tokens: consecutive steps
	     packed into one right-padded forward. Right padding is safe under causal
	     attention - a real token at position i only attends to j <= i, all real.
	     Groups are consecutive and never reordered, so CSV row order is unchanged.
	12.4 --profile, --no-save-activations, --benchmark-pt-write: measure the split
	     before tuning. Mac SSD does ~10k files/s (legacy container 19% faster and
	     16% smaller than zip); a network volume can be far worse, and which one the
	     host has decides whether 12.1 is sufficient.

24. Selection is method-dispatched; logit lens added beside the jlens
	The selection was jlens-shaped in three places at once -- KeptTokens.jlens /
	.random, ARMS = ("jlens","random") in record.py, and a hand-written
	RECORDED_SELECTIONS dict -- so adding a lens meant editing all three plus every
	call site. It is now one registry: telos_interp/jlens_utils/methods.py holds
	METHODS = {jlens, logitlens, random}, KeptTokens is arm-keyed by method name,
	and prepare's mode names (<lens>_direction, recorded_<method>) are GENERATED
	from it. Adding a future method is a registry entry.

	Two axes per method, both properties of the method rather than caller flags:
	which CSV it scores (None = no CSV), and whether it ranks by direction count or
	samples uniformly. `scored` has to live on the method because an unscored arm
	must record no counts -- split_next_action_manifest keys off that absence.

	The logit lens turned out to be nearly free. apply_lens_transport with an empty
	J_rows IS the logit lens: no transport, just final RMS norm + unembed. That is
	already the TARGET_LAYER=23 case, which is why the jlens is the identity there.
	So the two lenses are one function called two ways, and --lens both emits both
	CSVs from ONE forward pass -- the cost is a second unembed per chunk, not a
	second pass. Free correctness check, now a test: at layer 23 the two CSVs must
	be row-for-row identical, since the transports coincide there.
	They differ in exactly two ways: eligible layers (the jlens needs a fitted J,
	the logit lens needs nothing, so it covers every requested layer -- and can
	therefore select layers the jlens never could), and the transport itself.

	The awkward part: the tree was ALREADY pruned to jlens+random, ~5 layers per
	token. So a logitlens arm cannot be recovered by re-filtering -- the tokens it
	would pick are gone. delete_non_jlens_selected.py now refuses to widen an
	existing selection and says so, rather than deleting on the basis of an arm it
	cannot satisfy. The path that works is jlens_reasoning_tokens.py --extend:
	one CSV-only forward pass for the new lens (the CSV comes from the model, not
	from the tree, so pruning is no obstacle), gather only the .pt files not
	already present (the arms overlap heavily on genuinely direction-loaded
	tokens), and MERGE the arm into the record. Wrapped by
	scripts/jlens_extend_logitlens.sh, dry-run by default.

	The control arm is deliberately NOT redrawn on extend. The one in the record is
	a uniform draw over the FULL chain, taken before anything was deleted, so it is

	Record format is v2 (arms: {name: {config, picks}}), per-arm config because an

27. TOKENS_PER_TRAJ="all" in train_next_action_arms.sh
	The sweep knob from entry 23 had no "don't thin" setting -- the script always
	passed --tokens-per-trajectory. Passing a huge K works (thin_tokens keeps
	everything under the cap) but tags the probes *_top9999 and prints a
	per-trajectory budget it never applies, so "all" now OMITS the flag instead:

	    local token_args=()
	    if [ "$k" != "all" ]; then token_args=(--tokens-per-trajectory "$k"); fi

	split_next_action_manifest.py already treated the flag as optional and skips
	thin_tokens entirely when absent, so no Python change. Tags become
	${arm}_topall, splits land at ${prepared}_topall_{train,eval}. "all" means
	every token the arm's record holds -- the lenses' top-20 by direction_count,
	the control's 20 uniform draws -- NOT the union across arms. The three arms
	overlap only partially, which is the point: equal N, different chooser.

	Layer pinning has to happen at PREPARE time for the control, not at split.
	thin_layers ranks by layer_direction_count when counts are present and
	SAMPLES uniformly when they are not (entry 22) -- so --layers-per-token 1 gives
	the top-scoring layer for jlens/logitlens but a RANDOM one of the ~6 recorded
	layers for the control. Layer 15 is only guaranteed to be among the candidates,
	never to be the one drawn. Preparing the control with --layers 15 leaves it one
	row per token, after which --layers-per-token 1 is a no-op that picks it.

	The run this was written for -- all selected tokens, one layer each:

	  # lens arms: keep every recorded layer so the split can pick the top-scoring one
	  ARMS="jlens logitlens" LAYERS=7:23 OUT=/workspace/prepared/next_action \
	      ./scripts/prepare_next_action_arms.sh

	  ARMS="random" LAYERS=15 OUT=/workspace/prepared/next_action \
	      ./scripts/prepare_next_action_arms.sh

	  # train: every selected token, one layer per token
	  ARMS="jlens logitlens random" TOKENS_PER_TRAJ=all LAYERS_PER_TOKEN=1 \
	      PREPARED=/workspace/prepared/next_action ./scripts/train_next_action_arms.sh

	~3600 x <=20 x 1 = <=72k rows per arm, matched across arms. Note the two

35. Direction scoring becomes a LOGPROB, and layer selection becomes a CHOICE
    (2026-08-27, code only -- no GPU work yet, nothing on disk has changed)

	Two complaints about the selection pipeline, both fair, both now addressed.

	(a) THE SCORE THREW AWAY THE LENS' OWN BELIEF. A token was ranked by how many
	of its top-20 lens predictions are direction words. That counts a direction
	word the lens put first at p=0.4 exactly the same as one it put 20th at
	p=1e-6. The CSVs already had the information and were discarding it: topk
	returns values as well as indices.

	So the CSV now carries a `top_{i}_logprob` beside every `top_{i}` -- 20 more
	columns, computed from the same logsumexp the action logprobs already used, so
	the marginal cost is a subtraction. And *how* a row's hits become a number is
	now a registry, telos_interp/jlens_utils/scoring.py, dispatched by name the
	same way the methods are:

	  count         how many top-k predictions are direction words   (the original)
	  logprob_mass  logsumexp of the matched logprobs = log of the TOTAL
	                probability the lens puts on direction words
	  logprob_sum   sum of the matched logprobs

	A NOTE ON logprob_sum, because the obvious reading is a trap. "Sum the log
	probabilities" multiplies the probabilities. A token whose lens emits five
	direction words at logprob -3 sums to -15; one that emits a single word at -2
	sums to -2 and wins. Under a sum, every additional direction word makes a token
	score WORSE -- the exact inverse of what the count meant. And an empty sum is
	0, which is log(p=1), so a token with no direction word at all would be the
	best token in the trajectory. logprob_sum is implemented because it is the
	literal request and someone will want to see it, but logprob_mass is the one
	that means "how direction-loaded is this token": adding in probability space,
	more or better-ranked direction words can only raise the score, and it reduces
	to a belief-weighted count. Use logprob_mass. A no-hit row floors at
	NO_MATCH_LOGPROB (-40, ~4e-18) rather than 0 or -inf -- finite, JSON-safe, and
	orders of magnitude below any real top-20 logprob.

	Everything is "higher is better", so rank_tokens, rank_layers_by_direction and
	split_next_action_manifest.py sort by -score in every mode without knowing
	which one ran. --direction-score is on jlens_reasoning_tokens.py,
	delete_non_jlens_selected.py and prepare_activations_for_probing; the default
	stays `count` so no recorded invocation changes meaning under its feet.

	WHAT THIS COSTS ON DISK. Every CSV and every selection record out there is
	pre-logprob. read_direction_scores REFUSES a logprob mode on a CSV with no
	top_i_logprob columns rather than scoring every row as "nothing matched",
	which would rank every token by a tie and look exactly like a result. The fix
	is a CSV-only re-emit -- `--overwrite --no-save-activations` -- one forward
	pass per trajectory, no .pt written, so the pruned tree is untouched. Which
	mode a record's numbers are in lives in that arm's config.direction_score;
	absent means count, which is what every record on disk is.

	CAVEAT worth stating before the sweep: on a PRUNED tree, re-scoring with a new
	mode can only re-rank the tokens that survived. logprob_mass will order the
	~20 kept tokens differently than the count did, and that is a usable
	comparison (top-K off the same 20), but it cannot reach a token the count
	never selected. A genuinely logprob-selected arm needs a fresh selective
	gather, or an --extend arm, on a tree that still has the tokens.

	(b) THE PROBE WAS READING SEVERAL LAYERS AT ONCE. --layers-per-token 1 keeps
	each token's OWN best layer, so the dataset still spans the whole layer range
	and a single weight vector is asked to read layer 7 and layer 22 -- not a
	shared basis. This is a plausible reason the probe underperforms and entry 28's
	layer-distribution confound is the same disease.

	Added split_next_action_manifest.py --single-layer L|best (SINGLE_LAYER in the
	train_*_arms.sh pair): pin the WHOLE dataset to one layer. `best` takes the
	manifest's argmax by mean layer_direction_count.

	BUT that mean is biased and the bias is not small. A manifest holds a
	(token, layer) entry only where that layer was SELECTED, so a layer's mean
	there is conditional on having beaten the other layers of that token -- except
	layer 15, force-kept for every token, whose mean is unconditional. Comparing
	the two systematically favours whatever is rarely selected. The unbiased number
	comes from the CSVs, where every token is scored at every layer, pruned tree or
	not (pruning deletes .pt files, never CSVs). That is
	scripts/jlens_layer_profile.py + jlens_utils/layer_profile.py: mean direction
	score per layer over the whole tree, prints the table, names the argmax. Take L
	from there and pass it explicitly. The split script prints its own per-layer
	table with a coverage column so the conditioning is visible either way.

	Also: --single-layer at any layer but 15 DROPS the tokens that never selected
	it (only 15 is guaranteed present), so the token budget shrinks; the script
	reports by how much rather than letting the K in --tokens-per-trajectory
	quietly stop being K. And a control arm carries no scores and cannot pick a
	layer -- give it the same explicit L as the lens arm, or the arms stop
	differing only in their tokens.

	TEST NOTE. The CSV is no longer byte-stable across --batch-size /
	--forward-batch-size. It never really was: the batched GEMMs reassociate their
	reductions, and with ~400 float columns per row instead of 4 one of them
	eventually lands on a 4-decimal rounding boundary (observed: -4.5685 vs
	-4.5686). The three tests that asserted read_bytes() equality now compare the
	tables cell by cell, floats within 1.5e-4, everything else exactly -- which is
	the claim actually worth making. The pre-batching golden reference was extended
	to emit the new columns the naive way, so it still pins the optimisation.

	ADDENDUM to 35 (2026-08-27): the mass is now computed AT THE SOURCE, over the
	whole vocabulary.

	Entry 35's logprob_mass scores the CSV's top-20 columns, so it can only see
	direction words that made the top 20. That is a truncation, and it bites
	exactly where the signal is most interesting: a token whose direction belief is
	spread thinly across many words looks empty, and mass sitting at rank 21 is
	invisible. The fix is nearly free because the expensive object already exists.
	While the [b, vocab] logits are still on the device, gather every direction
	token id and logsumexp them: one gather over ~500 columns plus one reduction,
	against logits the unembed just paid for.

	NEW ARTIFACT: {stem}_{lens}_direction_mass.csv, written beside the analysis
	CSV. WIDE where the analysis CSV is long -- one row per reasoning token, one
	L{n} column per layer, each cell log P(any direction word) at that (token,
	layer). This is the (token x layer) table entry 35's plan wanted for analysis,
	and it is ~2% the size of the analysis CSV. An EMPTY cell means the lens
	covered no such layer; that is deliberately distinct from a cell holding the
	floor, which means covered-but-no-mass.

	New score mode `logprob_mass_full` reads it. `DirectionScore.source` ("topk" |
	"mass") is what routes a score to its artifact, and
	methods.score_artifact_path() is the single place that decision is made, so the
	filter, the pruner and the preparer cannot end up reading different files.

	THE TRADE, and it is the reason the top_i_logprob columns STAY. A top-k score
	can be re-scored against a DIFFERENT direction vocabulary from the CSV alone,
	no forward pass. A mass table is baked at gather time. Given round 1 and round
	2 point direction_tokens_full.json and grid_tokens_full.json at trees of the
	same shape, a mass table whose vocabulary is unrecorded is a column of numbers
	nobody can interpret six weeks later. So every table gets a
	`.meta.json` sidecar (vocabulary path, classes, token count, what was dropped,
	model, lens, layers), written only after the table itself lands.
	--no-top-logprobs exists for runs that will only ever score the mass table (it
	saves ~40% of the analysis CSV), but it is not the default and should not be
	unless the vocabulary is settled.

	VOCABULARY -> IDS. The vocabularies are stored as DECODED strings (" left")
	because string matching against the top_i columns is what scored them. A mass
	needs logit COLUMNS, so the strings go back through the tokenizer:
	resolve_direction_ids keeps a string only when it encodes to exactly one token
	AND that token decodes back to it. Both halves matter -- a multi-token string
	has no single column, and a lossy round trip would silently put mass on a
	different token than the vocabulary asked for. The notebooks' admissible()
	already filters to real gpt-oss-20b tokens, so a drop here means the vocabulary
	and the tokenizer disagree and the run says so.

	FOUND WHILE TESTING, worth knowing before reading any numbers: a per-layer cell
	is a real log-probability and is <= 0, but a TOKEN's score aggregates ACROSS
	layers with logsumexp, which adds probabilities belonging to different
	distributions (one per layer). It can exceed 0 on a token that is
	direction-loaded at several layers at once. That is fine -- it is only ever
	used to ORDER tokens and the order is monotone -- but it is not log P(anything)
	and must not be reported as one. Pinned in a test so it does not get "fixed".

	Costs nothing new on the GPU host: the CSV-only re-emit entry 35 already
	planned (--overwrite --no-save-activations) now produces the mass table in the
	same pass. Add --direction-mass-json explicitly on any run that is not
	gathering selectively, since it defaults to --signal-json which such a run does
	not set.

43. TWO MORE TRUNCATION GRIDS: ASKING THE MODEL WHERE THE LENS IS LOUD
    (2026-08-31)

	Entry 41(c) put the commitment on the FIRST tokens of the convinced sentence
	and noted that the rollout can only see it at that sentence's END, a median ~7
	tokens later. Entry 42(a) then showed that a sentence end is also the QUIETEST
	point of its sentence -- loudness falls ~2.2x from the second decile to the
	last and resets at the break. Both say the same thing about the instrument:
	`eos` samples the reasoning exactly where the lens has the least to say. This
	entry adds two grids that sample where it has the most. NOTHING ELSE ABOUT THE
	ROLLOUT CHANGES -- same model, same trajectories, same prefix+grid+suffix+
	reasoning[:cut]+final-prefix prompt, same greedy single-token read of the
	action. Only the cut positions differ.

	  scripts/inference_oss/truncation_strategies.py   <- new; the registry
	  scripts/inference_oss/run_inference.py --strategy
	  scripts/inference_oss/run_inference_strategies.sh

	THE THREE ARMS, by `--strategy`:

	  eos                        every reasoning sentence end, plus a no-reasoning
	                             cutoff and the end of reasoning. Unchanged, and
	                             byte-for-byte the old code path -- it is the
	                             baseline, re-run here over these trajectories.
	  jlens_argmax_per_sentence  one cutoff per sentence, at its LOUDEST token.
	                             Same sentence grid as eos; only the position
	                             inside each sentence moves.
	  jlens_top_k_global         the K=20 loudest tokens of the whole chain,
	                             wherever they fall, so the grid follows the lens
	                             rather than the punctuation.

	LOUDNESS IS ENTRY 42'S, unchanged: the layer-15 cell of the direction-mass
	table, log P(any direction word) over all 446 tokens of
	direction_tokens_full.json, i.e. sum(exp(logprob(t))) exponentiated. Ranking
	is done on the log directly (exp is monotone); the record carries both. The
	tables are read with their .meta.json sidecar, so the vocabulary each arm
	ranked against is recorded in the results JSON rather than assumed.

	THREE DESIGN DECISIONS worth knowing before reading the numbers:

	  * THE ENDPOINTS ARE KEPT IN EVERY ARM. Each jlens arm still gets the
	    no-reasoning cutoff first and the full-reasoning cutoff last, so all three
	    arms' first and last evals are the SAME prompt. Without that,
	    `final_sentence_accuracy` and `convinced_sentence_idx` would be measuring
	    different endpoints per arm and could not be compared at all.
	    `--no-endpoint-cutoffs` turns it off; do not, unless that is the point.
	  * THE TRAJECTORY SET IS PINNED BY --names-file. Loudness exists only where a
	    direction-mass table does, i.e. the 3,600 of
	    /workspace/activations/jlens_mass_l15, so the eos arm is pinned to the same
	    3,600 rather than to the 36,000 it originally ran on. Note this is the mass
	    tree's FULL 3,600, not entry 42's 2,880 -- nothing here trains a probe, so
	    the held-out 720 are not excluded.
	  * THE OUTPUT SCHEMA IS THE eos SCHEMA. `sentence_evals` is the ordered list of
	    cutoffs and `eos_token_pos` is the cut position, so analysis.py,
	    build_sentence_loudness.py and build_probe_rollout_join.py read all three
	    arms unchanged. What the strategy chose is added per eval: `cutoff_kind`,
	    the sentence the cut lands in on the eos grid (`cut_sentence_idx`,
	    `pos_in_sentence`, `sentence_len`), and its loudness (`dir_logmass`,
	    `dir_prob`). `n_reasoning_sentences` is the number of CUTOFFS in every arm
	    -- a misnomer under jlens_top_k_global, kept for the readers above;
	    `n_cutoffs` is the same number under an honest name.

	THE GRIDS REALLY ARE DIFFERENT, checked offline over 300 sampled trajectories
	(7,038 sentences, 0 mismatches against an independent recompute of the argmax
	straight from the CSVs):

	    arm                        cutoffs/step   prompts over 3,600
	    eos                            24.46            88,056
	    jlens_argmax_per_sentence      25.46            91,644
	    jlens_top_k_global (K=20)      21.89            78,816

	The per-sentence argmax sits at mean fraction .417 through its sentence and
	coincides with the sentence end in only 10.4% of sentences; only 3.4% of the
	top-K cutoffs are sentence ends. jlens_argmax_per_sentence has one cutoff more
	than eos per step because the full-reasoning endpoint is usually not the last
	sentence's loudest token.

	WHY K=20 AND NOT SOME OTHER K: it is the gather's own `--select-num-tokens
	20`, ranked by the same `logprob_mass_full` at the same `--select-candidate-
	layers 15`. So on these single-step trajectories jlens_top_k_global cuts at
	(essentially) THE TOKENS THE MASS-ARM PROBES WERE TRAINED ON. Checked against
	the recorded selections over 200 sampled steps: the cutoff set equals the
	`jlens` arm's picks exactly in 88.5% of steps, mean Jaccard .994 -- the
	remainder differ by a single token, which is what a tie or a rank-20 boundary
	looks like. That makes this arm the rollout counterpart of the probe arm token
	for token: same tokens, one read by a probe on the residual stream, the other
	by the model itself with the reasoning cut there. It also incidentally
	cost-matches eos (21.9 vs 24.5 cutoffs per step).

	*** THE CAVEAT TO READ FIRST. *** Entry 42(e)'s third control is this
	experiment's central confound, and here it is structural rather than
	incidental: the loudest token in a sentence is very often the direction word
	the model is writing down. On the dry-run trajectory the three per-sentence
	argmaxes are ` up` (mass .870), `(7,` (.130) and ` UP` (.686) while the
	sentence-final `.` is at .028. Truncating just after the model has typed "UP"
	and then asking it for its action is a much easier question than truncating at
	the sentence end, so a raw accuracy gain for the loud arms is NOT evidence
	that the commitment is readable earlier. The comparisons that survive it:
	  * restrict to cutoffs whose own token is not in the direction vocabulary
	    (`token` is recoverable from the mass table; `dir_logmass` is on every
	    eval), exactly as 42(e) did;
	  * compare at matched positions in the chain rather than raw means -- a
	    `random`-position control arm is the missing fourth strategy and is a
	    single registry entry in truncation_strategies.py (METHODS-style dispatch,
	    same shape as jlens_top_k_global with a seeded uniform draw of the same K).
	Do not report an arm-vs-arm accuracy without one of those.
